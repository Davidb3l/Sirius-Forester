# The Gate

`sirius gate AMT-n` decides whether an issue may advance. It exists because of one discovery, recorded in `src/gate.rs`'s own header:

> **`hayven affected-tests` is a SELECTOR, not a runner.** Its exit code means "selection computed", never "the tests pass".

A gate keyed on that exit code passes with **zero tests executed** — and both real gate runs to date did exactly that (`roots` matched, `tests: []`, exit 0). So Sirius owns the run-the-tests half itself.

## The five steps

1. Resolve changed files from a git range (`src/gitrange.rs`; default working tree vs HEAD).
2. Ask `hayven affected-tests --changed <files> --json` which tests those files can affect.
3. Decide whether that selection can be **trusted to be complete**.
4. Run the chosen tests via `gate.test_cmd`, through an explicitly resolved shell (see [The shell](#the-shell)).
5. Take the verdict from the **test runner's** exit code.

The governing rule is *"ran too much, never missed a test."*

## The trust bar

`decide_plan` is pure and unit-tested. A narrow (subset) run requires **all** of:

- the selector command succeeded and its stdout parsed as JSON (`sel.ok`)
- **every** changed file mapped to an indexed entity (`roots >= changed files` — a partial
  mapping means the unmapped files contributed nothing to the selection)
- there is at least one runnable test id, and none is dash-leading (a flag-like id from the
  daemon would reach the test runner as a *flag* — `pytest -q --co` exits 0 running nothing)
- the selector's own `note` raises no under-reporting flag
- **no global-impact file changed**

Anything short of all of that is *doubt*, and doubt defers to `gate.fallback`. Fleet iterations in isolated worktrees are ALWAYS doubt (the daemon's graph reflects the main checkout, not the worktree) — `evaluate_isolated` skips selection with a reason that reads as the routine note it is (`selection skipped in an isolated worktree (the code graph watches the main checkout) — ran the full suite`, or the `fail` / `pass-with-warning` equivalent), not as a cause of failure — and the `unconfigured` verdict is the one marked `structural` — the retry budget skips it, since no fresh agent attempt can change it.

`note_is_suspect` matches the selector's self-reported caveats: `stale`, `cold`, `under-report`, `under report`, `under_report`, `no traces`, `may under`. This matters in practice — an untraced index emits `"no traces yet — static only, may UNDER-report"`, and that alone forces the full suite even when the selection looks narrow and healthy.

`is_global_impact` forces a full run for any changed file under `.github/`, or named `Cargo.toml`, `Cargo.lock`, `build.rs`, `package.json`, `package-lock.json`, `bun.lockb`, `tsconfig.json`, `conftest.py`, `pyproject.toml`, `setup.py`, `setup.cfg`, `tox.ini`, `pytest.ini`, or beginning `requirements`. These are files whose blast radius a static graph cannot bound.

## Plans and fallback

`GatePlan` has four shapes: `Subset(ids, reason)`, `Full(reason)`, `Block(reason)`, `WarnPass(reason)`. Under doubt, `gate.fallback` picks between the last three:

| `gate.fallback` | Behavior under doubt |
|---|---|
| `full-suite` *(default)* | Run everything. The only safe posture. |
| `fail` | Block rather than run everything — for suites too slow to run in full. |
| `pass-with-warning` | Advance anyway, explicitly opting into the miss risk. |

`pass-with-warning` files an Ametrite comment saying it advanced **without running tests**, so the choice is visible on the board rather than silent.

## Fail-closed

With no `gate.test_cmd` configured (or a blank one), a plan that requires running tests yields `plan: "unconfigured"` (`reason_code: unconfigured_test_cmd`, `structural: true`) and does **not** pass. The gate refuses to bless code it could not test — asserted by `execute_without_test_cmd_fails_closed`, which also checks that no command was run at all. Its `reason` says outright that no test failure occurred and points at `sirius doctor`, whose `gate_configured` check prints the command detected for the repo.

To keep that state rare, `sirius init` writes a starter config with `gate.test_cmd` pre-filled (`Config::default_json_for_root` → `detect_test_cmd`, reading only workspace-root markers, first match wins): `Cargo.toml` → `cargo test --workspace`; a `package.json` that declares a non-empty `scripts.test` → `bun test` with a `bun.lock`/`bun.lockb`, else `npm test`; `pyproject.toml` or `pytest.ini` → `pytest`; `go.mod` → `go test ./...`. Nothing detectable leaves it `null`. A legacy `"test_cmd": null` still parses.

## The shell

`test_cmd` — with any subset ids appended — is handed to a shell as **one script string** (`shell::run_in_shell`), so `&&` and `|` act as operators. Which shell is resolved explicitly by `shell::resolve_shell`, never inherited from whatever launched Sirius:

1. `SIRIUS_SHELL`, if set, wins verbatim (`cmd`-named programs get `/C`, anything else `-c`).
2. On unix: `/bin/sh -c` — absolute, so an empty `PATH` cannot break it.
3. On Windows: the first `sh.exe` / `sh` on `PATH`, resolved to an absolute path, with `-c`. `bash` is never probed by name — `System32\bash.exe` is the WSL launcher.
4. Otherwise on Windows: `%ComSpec%` (default `cmd.exe`) with `/C`. On Windows the script goes on cmd's command line raw, as `/S /C "<script>"`, so its own quotes survive.

Subset ids are quoted for the resolved shell (`shell_quote`): ids made only of `[A-Za-z0-9_\-./:=]` pass bare; otherwise POSIX single quotes, or for `cmd.exe` MSVC-quoting with every cmd metacharacter (quotes and `%` included) caret-escaped (`cmd_quote`). `execute_plan` takes the shell as a parameter, so gate tests pin `ShellCmd::posix_sh()` instead of depending on the developer's box. A shell that cannot be spawned yields `reason_code: shell_spawn_failed` with `ran_tests: false` and a detail that names the shell and says it is not the test binary.

Only `gate.test_cmd`, `--agent-cmd` (see [subsystems/loop](./loop)), and `worktree.setup_cmd` ([below](#environment-faults-and-worktree-setup)) go through this resolution; the review, integration, and review-canary spawns still run literal `sh -c`, since each wraps its command in a Sirius-built POSIX `cd "$…" || exit 1; …` script.

## Outcome

On pass: `amt issue update --status <target>` advances the issue (a `pass-with-warning` also files its warning comment). On fail: an issue comment `sirius gate FAILED (tier …, plan …, reason <reason_code>): <reason>.` is filed; when the run produced output it continues `Output tail:` and the [error tail](#the-error-tail) in a Markdown fence, and when the output looks like an [environment fault](#environment-faults-and-worktree-setup) a closing line quotes the offending output line. The status is left untouched. Either way a `gate_tier` policy event lands in the ledger carrying `plan`, `reason`, `reason_code`, and `tests_run` (plus `structural`, `error_tail`, and `env_fault` as a bool on a fail; `advanced_to` on a pass).

## The error tail

A verdict's `detail` keeps the last 20 non-empty lines of combined stdout+stderr. `error_tail` narrows that to the last `ERROR_TAIL_LINES` (15) non-empty lines, capped at `ERROR_TAIL_MAX_BYTES` (2048) — the **end** is kept, cut onto a line boundary where one exists and marked with a leading `…`. Control characters other than newline and tab become spaces first: a NUL cannot go into an environment variable, and the fleet hands the tail to the next attempt as `SIRIUS_LAST_GATE_TAIL`. It is empty when nothing ran. `fenced` wraps it in a fence longer than any backtick run inside it, so the output cannot close its own fence.

The fleet files its own failure comment, `loop_fail_comment`: `sirius: gate failed [<plan>, <reason_code>] — output tail:`, the fenced tail, then `Plan: <reason>` last — the selection note is demoted because it is never the cause of a red suite (SIRF-48). With no output (blocked, unconfigured) the reason *is* the explanation and stays inline. A note on what the env-fault re-gate did, when one was considered, is appended.

## Environment faults and worktree setup

A fresh fleet worktree has the tracked files and nothing else — no `node_modules`, no `.venv` — so a gate over it can fail on the *environment* rather than the code (SIRF-50). On a `tests_failed` verdict only, `env_fault_line` scans the full output and sets `GateVerdict.env_fault` to the first line that is:

- a missing-dependency message: `Cannot find module`, `Cannot find package`, `ERR_MODULE_NOT_FOUND`, `ModuleNotFoundError: No module named`, `error[E0463]: can't find crate` — **except** a `Cannot find module/package` naming a relative or absolute path (`'./x'`, `'/abs/x'`, `C:\…`), which is the code importing a file that does not exist;
- the shell reporting the test runner itself missing — `<runner>: command not found` / `<runner>: not found`, with `<runner>` the program of `test_cmd` matched as a whole word;
- any such `not found` line when the exit code is 127.

The bar is "plausibly the environment": a false positive costs one setup re-run and one re-gate, a false negative a work attempt. `sirius gate` only reports it (the comment's closing line, `env_fault: true` on the ledger event). The fleet acts on it: in a fleet worktree with a setup command, the loop re-runs setup and gates again — once per work/fix pass, without consuming a `retry_budget` attempt; still failing is an ordinary gate failure (see [subsystems/loop](./loop)).

`run_setup` runs `worktree.setup_cmd` (see [subsystems/policy-config](./policy-config)) through the resolved shell in the runner's cwd — the worker's worktree — supervised by `Runner::run_agent` with a wall clock (`SetupOpts.timeout`, from `worktree.setup_timeout_secs`) and its output streamed to `SetupOpts.log_path`. A process-wide `SETUP_LOCK` serializes setups, since package managers contend on their shared caches; while it waits for a sibling's setup, and while it runs, the heartbeat callback fires every `heartbeat_interval`, so the caller's leases do not lapse. `Err` names the command and carries its exit code or the timeout, plus an error tail read back from the log.

`setup_fingerprint` is `git ls-tree HEAD --` over `SETUP_LOCKFILES` (`bun.lock`, `bun.lockb`, `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`, `uv.lock`). `write_setup_stamp` records it as `sirius-setup-stamp` inside the worktree's git dir — never a file the work could commit — and `setup_is_stale` reports a mismatch, so an iteration whose fresh base changed a lockfile re-runs setup. With no stamp to compare, it reports not stale.

## Reason codes and exit 3

`plan` is human copy and gets reworded; `reason_code` (`gate::reason_code`) is the stable machine contract:

| `reason_code` | Meaning |
|---|---|
| `pass` | tests ran, runner exited 0 |
| `tests_failed` | tests ran, runner failed — retryable |
| `blocked_by_policy` | `fallback = fail` refused to run the suite under doubt |
| `passed_without_tests` | `fallback = pass-with-warning` advanced without running anything |
| `unconfigured_test_cmd` | no `gate.test_cmd`; the only `structural: true` verdict |
| `shell_spawn_failed` | the shell itself could not start |

`sirius gate` exits **3** for every failing verdict, unconfigured included — exit 3 is the published "gate blocked" code (CONTRACTS §2) and the sirius worker Skill keys its release-without-advancing path on it, so no fourth code was minted. The `--json` envelope (`cmd_gate`) carries `reason_code` and `structural` alongside `plan`, `ran_tests`, `advanced_to`, `tests_selected`, and `comment_filed`; in human mode an unconfigured verdict also prints its `reason` to stderr.

<Callout type="warning">
**Naming wart worth knowing.** `GateOutcome.tests_selected` is populated from `GateVerdict.tests_run`, not from the size of the selection — its own doc comment says "Count of tests actually run (0 for a full-suite run — the runner decides)". A full-suite run therefore reports `tests_selected: 0` while having run the entire suite. `CONTRACTS.md` §2 documents the field by its name. Read `plan` and `ran_tests` for the truth.
</Callout>
