# The Ledger

`.sirius/sirius.db` is Sirius's **only** write target. SQLite in WAL mode, `PRAGMA user_version` = `SCHEMA_VERSION` (currently `1`). Created by `sirius init`; read read-only by the console.

It is an **audit log, not a second brain** — delete it and no work is lost, only the trail of how it happened. It is git-ignored and branch-invariant, because the ledger is a fact about work, not a code snapshot.

The authoritative schema DDL is [`CONTRACTS.md` §1](../../CONTRACTS.md); `apply_schema` in `src/ledger.rs` is what actually runs.

Parallel fleet workers each hold their own connection; WAL plus a 5-second `busy_timeout` (installed before the pragmas) serialize the concurrent writers.

`Ledger::open` refuses a missing **or uninitialized** db: it opens without SQLite's CREATE flag and probes `meta.schema_version` before handing the connection out. A zero-byte or never-init'ed file used to "open" fine and then fail every write — each failure swallowed at its call site, which is how a fleet once ran for hours against a permanently-empty ledger with zero diagnostics. Failed ledger writes in the loop now also warn on stderr (`ledger_warn` in `src/run.rs`).

## Five tables

| Table | Holds |
|---|---|
| `meta` | `schema_version`, `created_at`, `sirius_version` |
| `workers` | one row per worker id (`sirius/oak`), with `status` and `last_seen_at` |
| `iterations` | one row per loop pass: issue, entities, outcome, gate result, oracle verdicts, tokens, duration, receipt |
| `receipts` | provenance stamps — `kind` (`issue`/`decision`), `ref`, `symbols`, `forward_ok`, `reverse_ok` |
| `policy_events` | why the policy engine did what it did |

`receipts` is created **before** `iterations` in `apply_schema`, because `iterations.receipt_id` references it and foreign keys are ON.

## The write API

- `upsert_worker(id, status)` — insert-or-refresh, so a worker rejoining updates `last_seen_at` rather than erroring.
- `start_iteration(worker, issue)` → row id; `finish_iteration(...)` fills in outcome, gate result, oracle verdicts, tokens, duration, receipt. Two calls, one row.
- `insert_receipt(kind, ref, symbols, forward_ok, reverse_ok, worker)` → row id. `forward_ok` / `reverse_ok` are stored independently, so a half-landed stamp is recorded honestly rather than as a success or a failure.
- `log_policy_event(iteration_id, kind, detail)` — `detail` is arbitrary JSON.
- `count_policy_events(kind, limit)` — counts how many of the most recent `limit` events **of any kind** are of `kind`. The window comes first, then the filter — the reverse order (filter-then-limit) counted all-time occurrences capped at `limit`, which latched adaptive claiming into pre-claim forever after two 409s ever. This is what adaptive claiming reads to sense contention; see [subsystems/loop](./loop).

## Read API for the console

`schema_version()`, `meta(key)`, and `data_version()` are marked `#[allow(dead_code)]` — they are the read surface the console consumes over WAL, not called by the CLI itself. `data_version()` wraps `PRAGMA data_version`, which bumps on any external write; the console polls it to drive SSE updates without a filesystem watcher.

## No chrono

`now_iso8601()` / `format_iso8601()` implement the civil-from-days algorithm by hand rather than pull in `chrono`, which is outside the allowed crate set (`rusqlite`, `serde`, `serde_json`, `clap`, `regex`). Both are unit-tested against the epoch and a known 2026 timestamp.
