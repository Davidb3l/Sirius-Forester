# The Loop

`sirius run --workers N --agent-cmd "<cmd>" [--review-cmd "<cmd>"]` drives the fleet. One iteration is up to ten phases, and `run_iteration` is deterministic and fully mockable — the loop's correctness properties are tested through it without a live `amt`, `hayven`, or agent.

```
claim → map → lock → brief → work → gate → [review ⇄ fix] → receipt → release
```

Those ten strings are the `PHASES` constant (`review` and `fix` appear only when the review stage is on) and appear verbatim in the NDJSON `phase` field. `sirius run --json` streams one JSON object per line to stdout (each event is a single atomic `write_all`, so parallel workers never interleave a line).

## Parallel workers in isolated worktrees

`cmd_run` spawns each worker as a real OS thread (`worker_loop` in `src/main.rs`) — the old v1 loop ran them sequentially, so `--workers 3` gave three roster names and zero parallelism. Each worker gets:

- its **own git worktree** at `.sirius/worktrees/<worker>` (created from the fleet base commit, removed at exit). Agents, git diffs, and gate test runs all execute inside it — parallel agents in one shared checkout would cross-contaminate every baseline diff and race on git's `index.lock`. A worker whose worktree cannot be created **stops**; there is deliberately no fallback to the shared checkout.
- its **own ledger connection** (WAL + a 5s busy timeout serialize concurrent writers) and its own `amt`/`hayven` adapters, which run against the repo, not the worktree.
- a per-issue branch, stamped at COMPLETION: each iteration hard-resets the worktree to the fleet base and works **detached** (a parked branch would block a sibling worktree from re-claiming the same issue); on a completed iteration sirius auto-commits any uncommitted agent work and points `sirius/<issue>` at the result — so completed work survives after the worktree is torn down (non-committing agents included), and one iteration's leftovers can never poison the next issue's gate. If preserving fails, the issue is NOT advanced.

Because the code-graph daemon watches the MAIN checkout and cannot see worker worktrees, fleet iterations never trust `affected-tests` selections — the gate always takes the doubt path (full suite under the default fallback). Narrow selection remains for the serial `sirius gate` CLI. Worktrees are created serially by `cmd_run` before any thread spawns (concurrent `git worktree add/prune` race on `.git` locks), and a `.sirius/run.pid` guard refuses a second fleet in the same repo — a second `sirius run` would otherwise force-remove the first fleet's live worktrees.

Workers share an atomic iteration budget (`--max-iterations`, refunded for idle NoWork probes so the cap counts real iterations) and a failure flag (exit code 1 if any worker trips its 5-consecutive-error budget). A worker whose `NoWork` answer carries `retry_after` (issues exist but are leased) waits briefly — capped at 30s, three probes — before giving up, so the pool doesn't drain while siblings may still release work back to the board. A REFUSED lease refresh at the pre-spawn check (amt answers `claimed:false` — the lease lapsed) aborts the iteration before the agent spawns, instead of putting two agents on one issue. `sirius run` also **refuses to start** when `gate.test_cmd` is unset (unless `gate.fallback` is `pass-with-warning`): every gate would fail closed, burning a full agent run per issue while advancing nothing.

## The agent contract

Every agent and reviewer process gets `SIRIUS_ISSUE`, `SIRIUS_WORKER`, `SIRIUS_WORKTREE`, `SIRIUS_BASE`, `SIRIUS_PHASE` (`work` | `review` | `fix`) and `AMT_AGENT=sirius/<tree>` in its environment, and `{issue}` / `{worker}` are filled in in `--agent-cmd` / `--review-cmd` (`template_cmd`). `AMT_AGENT` — plus `--author sirius/<tree>` on every comment and decision Sirius itself writes — attributes fleet work on the board to the worker, not to the human running the fleet. The gate no longer moves the issue status itself: the release step does, once, after any review.

The WORK⇄GATE loop is a reusable closure (`run_work_gate`) returning `WorkGate::Done { work_ok, gate_result, exit, log, timed_out }` or `WorkGate::Exit(outcome)` for terminal paths that already did their bookkeeping (lease lost, a WORK agent killed by the timeout). Review fix rounds reuse it with `SIRIUS_PHASE=fix`, so they get the same heartbeat, timeout, log capture, baseline diff, and retry budget. When the agent fails, the release comment names it ("agent exited 1 (see .sirius/logs/…)") rather than blaming the gate.

## Models and the usage-limit pause (SIRF-26)

`cmd_run` resolves the fleet's models once (`models::resolve`: `--model` > `models.default` > `$SIRIUS_PARENT_MODEL`; `--review-model` > `models.review` > the worker model) and **refuses to launch** (exit 2) with no worker model unless `--allow-default-model` — naming the model every Claude worker would otherwise silently inherit from `.claude/settings*.json` (`check_models`). It emits a `fleet start` NDJSON event with the resolved models. Per iteration, the claimed issue's Ametrite `labels` pick the worker model (`models::model_for`: first matching `models.routes` entry; fix rounds of un-routed tickets use `models.fix_floor`), and it is injected as `ANTHROPIC_MODEL` + `SIRIUS_MODEL` (reviewer: `ANTHROPIC_MODEL` + `SIRIUS_REVIEW_MODEL`) and the `{model}` placeholder; claim events carry `model` / `review_model`.

All workers share `Fleet.pause` and `Fleet.fallback`. When a FAILED agent or reviewer's last output lines carry a fleet stop (`models::fleet_stop`: a usage/plan limit, a model this CLI version cannot run, or a logged-out CLI), `on_usage_limit` decides by the tier the agent RAN on: a limit/unsupported-model hit on the primary tier with a `models.fallback` configured switches the WHOLE fleet to the fallback tier (announced once: NDJSON `{"event":"fleet","phase":"fallback"}`, spine `fleet.fallback`) and retries the failed phase **in place** on it (work/fix: the WORK⇄GATE loop continues without consuming an attempt; review: a `fell_back` review event + ledger row, then the same try again). Models are re-resolved per spawn from `models::active`. A hit on the fallback tier, with no fallback, or a logged-out CLI pauses the fleet: a work-phase hit returns the issue to `todo` untouched (`usage_paused`: no deadend, `fleet.paused` + `job.blocked`), a fix-round hit reverts to the last reviewed checkpoint and escalates, a reviewer hit is not retried; every worker re-checks the pause before each claim and each spawn. `sirius run` then exits **4** after a `{"event":"fleet","phase":"paused"}` event. Agent logs live under the fleet's absolute `.sirius/logs`.

## Review ⇄ fix (SIRF-23)

With `review.cmd` set (or `--review-cmd`), work that passes the gate in a fleet worktree goes through `run_review_stage` (the pure contracts live in `src/review.rs`):

1. **Checkpoint** the worker's uncommitted work, so the reviewer sees exactly `base..HEAD` and a tampering reviewer can be undone with one `reset --hard`.
2. **Renew both leases** (`renew_checked`) — a refused amt lease aborts the iteration via the shared `lease_lost` unwind, without releasing an issue that is no longer ours.
3. **Review** in a fresh `sh -c 'cd "$SIRIUS_REVIEW_DIR" || exit 1; <cmd>'` process with stdin closed (agents are non-interactive). The findings are the reviewer's final message (`review::findings_json_in` over its captured log) or `$SIRIUS_REVIEW_OUT` if it could write one — so a reviewer needs only read tools. With `review.against = current-base-merge` (default) the review tree is a throwaway detached worktree with the checkpoint merged onto the current tip of `base_ref`; a merge conflict skips the reviewer and becomes blocking `conflict` findings. Its `git worktree add/remove` go through a process-wide mutex (`worktree_admin`).
4. **Enforce read-only**: `tree_fingerprint` (HEAD + porcelain status + diff) before/after; a change is reverted and the round is `tampered`. Missing/malformed JSON, a timeout, or tampering is a review error: retried once, then `on_review_error`.
5. **Fix**: on confirmed blocking findings with rounds left, run the worker in fix mode, then re-gate; the next review sees each finding next to the worker's `fixed`/`rebutted` response. A fix agent failure or timeout, or a gate it cannot repair within `retry_budget`, reverts to the last reviewed checkpoint and escalates — gate-passing work is never traded for a broken fix.
6. **Escalate** on exhaustion or error: `advance-flagged` (advance, label `review:open`, comment the open findings) or `release` (back to `todo`, ledger outcome `deadend`).

Every round writes a `review_rounds` ledger row, an NDJSON `review` event, an issue comment, and `review.*` spine events; the receipt's decision title carries the summary (`ReviewSummary::line`). A diff that is empty or touches only `skip_paths` skips the stage.

## Claim order is law

**Ametrite issue first, Hayvenhurst entities second; release in reverse.**

On a hard entity overlap (409), the issue is released back with a comment naming the blocker. Sirius never holds an issue while spinning on a code lock — that is the rule that keeps a stuck worker from parking work nobody else can take.

`lock_entities` walks the entity list in order, accumulating `acquired` claim ids. On any failure it returns without releasing anything; the caller unwinds. `LockResult` carries four shapes: `Locked { claim_ids, verdicts }`, `Overlap { blocker, acquired }`, `OracleBackoff { detail, acquired }`, and `Failed { detail, acquired }` — the last is an *operational* claim failure (daemon unreachable, wrong project, crashed CLI) that surfaces as `IterationOutcome::Error` so the run loop's error budget applies, instead of masquerading as contention and retrying forever.

The `verdicts` vector is parallel to `claim_ids` and records how each claim was actually obtained — `"registered"` (clean) or `"forced"` (oracle-conflicted, then forced under `Oracle202::ForceWithBudget`). It is written to the ledger verbatim rather than fabricating a uniform `"registered"` vector.

## Two failure modes that used to be silent

Both were fixed and both are worth knowing, because the naive version of each looks like it works:

**A `Registered` verdict with no claim id is treated as a claim failure.** The daemon can register a claim and hand back nothing releasable. Pushing the entity *name* as a stand-in id — the old behavior — makes the later `hayven release` silently fail and leaks the lease. Sirius now unwinds instead: it never manages a lease it cannot release.

**Releases are retried and logged.** `release_entity_checked` and `release_issue_checked` both retry with exponential backoff, and on final failure shout to stderr **and** write a `release_failure` policy event. The earlier `let _ = amt.release(...)` swallowed failures, leaving an issue silently locked to a dead worker. A leaked lock is never silent now.

## Adaptive claiming

`claim_decision` picks between `PreClaim` and `RelyOnGate`:

| `claim_mode` | Behavior |
|---|---|
| `always` | always pre-claim entities before work |
| `never` | never pre-claim; rely on the gate to catch collisions |
| `adaptive` *(default)* | read contention from ledger history |

Adaptive counts recent `backoff_409` policy events: **2 or more** within the last **20** sampled events flips it to `PreClaim` (`ADAPTIVE_409_THRESHOLD`, `ADAPTIVE_WINDOW`). Contention is sensed from what actually happened, not configured up front.

## Iteration outcomes

`IterationOutcome` is one of `NoWork { retry_after }`, `Completed`, `ReleasedOverlap`, `Deadend` (gate failed for good — retry budget exhausted, or a structurally-unpassable gate such as an unconfigured `test_cmd` that skips retries entirely; or a review escalated with `release`; deadend note filed), or `Error(String)`. Each pass writes exactly one `iterations` row.

## Two output streams, deliberately separate

- **NDJSON on stdout** — iteration phases, for whoever is watching the run.
- **The suite spine** (`.suite/`) — past-tense `job.*` / `gate.*` / `review.*` / `receipt.*` facts for other tools.

They have different vocabularies on purpose, so they never collide. The spine is optional (`None` disables it, as in tests) and best-effort. See [subsystems/suite-spine](./suite-spine).

## Reading the amt claim shape

`amt claim` does not return `{claimed: bool}` on success — it returns the full issue object. `issue_id` keys success off the presence of `id`; the no-work shape is `{"claimed": false, "retry_after": N, ...}`. This delta is recorded in [`CONTRACTS.md` §6](../../CONTRACTS.md).
