# Architecture Overview

Sirius Forester is a **local-first fleet foreman for AI coding agents** — a Rust CLI that claims work from Ametrite, locks the code it will touch in Hayvenhurst, runs an agent against it, gates the result on real tests, and stamps two-way provenance. The code is small modules in `src/` (the map below is the complete list), plus a zero-dependency Bun console under `web/`.

This doc is the map of the code. It deliberately does **not** restate the design rationale — that lives in prose already:

- [`docs/architecture.md`](../../docs/architecture.md) — the three stores, the five contract facts, what is measured and where
- [`CONTRACTS.md`](../../CONTRACTS.md) — the authoritative ledger schema, CLI surface, config shape, and the ground-truth deltas against the installed `amt` / `hayven`
- [`README.md`](../../README.md) — what the tool is for

Those files are the *why*. The Catryna docs under `.docs/` are the *what the code does now*, anchored to source so drift is detectable.

## The one invariant everything rests on

**One write path per store, and Sirius owns only its own.**

| Store | Owner | How Sirius touches it |
|---|---|---|
| `.ametrite/ametrite.db` | Ametrite | writes **only** through `amt … --json` |
| Hayvenhurst index / daemon | Hayvenhurst | `hayven` CLI or `http://localhost:7777` |
| `.sirius/sirius.db` | **Sirius** | its only write target — see [subsystems/ledger](../subsystems/ledger) |

Sirius never opens either parent's SQLite for writing. The console (`web/`) reads all three read-only and mutates *only* by shelling `sirius <cmd> --json`.

## Subcommands

`src/cli.rs` defines exactly nine (`Init`, `Doctor`, `Link`, `Why`, `Gate`, `Escape`, `ReviewCanary`, `Integrate`, `Run`). Every one takes `--json`.

```
sirius init            create .sirius/sirius.db beside an existing .ametrite/
sirius doctor          five contract facts live + plugin-handoff advisory
sirius link <AMT-n>    stamp two-way provenance (--decision D-n for decisions)
sirius why <target>    explain a symbol's issues/decisions, or an issue's symbols
sirius gate <AMT-n>    select affected tests, run them, advance on pass
sirius escape <AMT-n>  record a defect that got past review (--automated-by retires a kind; --list)
sirius review-canary   replay escapes + patch canaries through the reviewer, report recall
sirius integrate       build the integration frontier, run integration.cmd on it (red → issue + optional stop-the-line)
sirius run             the loop, --workers N --agent-cmd "<cmd>" --model <id> [--review-cmd "<cmd>"] [--review-model <id>]
```

Exit codes follow the suite convention: `0` ok, `1` operational failure, `2` usage error, `3` soft-block. `sirius doctor --json` is the discovery handshake and deliberately **exits 0 even when unhealthy** — a peer that exits non-zero is read as ABSENT, so an unhealthy-but-present tool must report its health in the envelope body, not the exit code (`doctor_exit_code` in `src/main.rs`).

## Workspace discovery

`Workspace::discover` walks up from the cwd for `.ametrite/ametrite.db` and `.hayven/` — but **never into `$HOME` or above** (both paths canonicalized first): `~/.ametrite` and `~/.hayven` are the parents' global state dirs, not workspace markers, and adopting them once fabricated ".hayven/ present" for repos that had neither. Candidates are type-checked (`.hayven` must be a directory, `ametrite.db` a file). `.sirius/` is placed beside `.ametrite/` when found, otherwise in the starting directory. Sirius mints no registry of its own.

## Testing seam

Every external process goes through the `Runner` trait in `src/shell.rs`, and `MockRunner` records the exact command lines. That is why the loop's correctness properties — claim order, 409 unwind, receipts, gate fail-closed — are unit-testable without a live `amt`, `hayven`, or agent.
